1. Platform Overview

1.1 What the platform does

Orvexa Cloud is a multi-tenant software-as-a-service platform for direct-to-consumer (D2C) brands. One codebase serves many independent online stores. Each store ("tenant") has its own branding, catalog, orders, customers and an isolated database, while Orvexa Tech operates all of them from a single super admin console.

The platform covers the whole merchant lifecycle:

  • Onboarding: merchant applications and leads are reviewed by the super admin, who approves them and provisions a new store.
  • Operations: each store owner manages products, orders, customer messages, homepage content and settings in the seller dashboard.
  • Selling: shoppers browse a branded storefront, add products to a cart, check out and track their orders.
  • Governance: subscriptions, domains, credentials and a full security audit trail are controlled centrally.

1.2 The three application layers

The single React application renders one of three "layers" depending on the URL. They share code, types and the API layer but present completely different interfaces.

1.3 Admin portal at launch

The Orvexa marketing website (formerly PlatformWebsite.tsx) has been removed from this application because it will be hosted on a separate platform. Opening the application root now shows only the admin sign-in screen; after successful authentication the administrator lands directly in the Super Admin Portal.

  • The marketing site, its "Client-Facing Website" toggles and the "Apply as Merchant" storefront footer link were removed.
  • Only the super admin account can sign in on this screen; seller credentials are rejected.
  • Storefronts and seller dashboards are unchanged and remain reachable through their own URLs.
Note. Merchant applications now arrive from the externally hosted marketing website through the signed signup endpoint described in Section 9.5.

3.1 Layer and tenant resolution

src/lib/tenant-resolver.ts decides which layer to render (resolveApplicationLayer) and which store to load (resolveTenantSlug). Rules are checked in this order:

#ConditionResult
1?panel=admin or ?admin=trueAdmin layer
2?panel=dashboard|seller or ?seller=trueSeller dashboard
3?panel=storefront|storeStorefront
4Path /admin, /dashboard, /seller, /store/…Matching layer
5?tenant= or ?store= presentStorefront
6Subdomain (production only): admin. / app., seller., merchant. / any otherAdmin / Dashboard / Storefront for that slug
7Anything else (root URL)Admin layer (sign-in screen)

Subdomain detection is skipped on preview hosts (vercel.app, netlify.app, github.io, pages.dev). Reserved subdomains are admin, app, api, www, mail, staging. On localhost the tenant defaults to lunar; on custom domains the full hostname is used as the lookup key.

3.2 Backend-first with offline fallback

The API modules in src/api/ call the Express backend first. In demo mode only (import.meta.env.DEV or VITE_DEMO_MODE=true), a failed request falls back to mock-store.ts, which keeps tenants, applications, products, orders and credentials in localStorage. Outside demo mode no passwords are kept in the browser and sign-in always goes to the backend.

3.4 Multi-tenant data isolation

  • Master database (orvexatech_master): tenants, applications, admin users, audit logs, refresh tokens, platform metrics.
  • Database per store: each tenant gets orvexa_tenant_<slug>, built from MONGODB_TENANT_BASE_URI + slug, holding products, orders and reviews.
  • Bring Your Own Database (BYODB): a store can be pointed at its own MongoDB cluster (mongodb+srv:// only). Owners can do this from the dashboard when ALLOW_CUSTOM_DATABASES=true; operators can use npm run tenant:set-db (Section 13.5). The backend tenantResolver middleware routes that store's queries to it. A URL without a database name uses orvexa_tenant_<slug>.
  • The store is taken from the URL path only; an unknown store is a 404 and never falls back to another store.
  • requireTenantAccess middleware ensures a seller or staff token can only act on its own store. Cross-tenant access is covered by automated tests.

4. Super Admin Portal

The Super Admin Portal is the control centre for Orvexa Tech. It is the first and only screen at the application root and requires authentication.

4.1 Sign-in and lockout

Figure 4.1 — Admin sign-in shown at application launch
  • Implemented in src/components/auth/AdminLogin.tsx; page title "Sign In | Orvexa Admin Portal".
  • Calls authService.loginAdmin() and accepts the result only if the role is super_admin. Seller and staff credentials are refused.
  • Lockout: after 5 failed attempts sign-in is locked for 60 seconds, even for correct credentials. The remaining attempts are shown after each failure.
  • No demo credentials or hints are displayed. A Show/Hide toggle reveals the password.
  • Every success and failure is written to the audit trail as ADMIN_LOGIN_SUCCESS / ADMIN_LOGIN_FAILED.
  • The session persists across page refreshes. Sign Out (bottom of the sidebar) clears it and returns to the sign-in screen.
  • Store-owner password reset links (?reset_token=) still open the reset dialog while signed out.

4.3 Merchant Applications

Figure 4.3 — Merchant application queue

Lists every application with brand, owner, contact, niche, requested subdomain and message. Applications from the marketing website (Section 9.5) also show the chosen plan, billing cycle and quoted price, country, any migration request (for example from Shopify), consent evidence (terms version and acceptance date, marketing opt-in) and campaign source. The admin can Approve (which provisions the store — see Section 5) or Reject; the owner receives the decision by email. Status changes are persisted through PUT /api/admin/applications/:id/status and audit-logged.

  • Address clashes: if the requested address is reserved or already taken, the card shows a warning and a field for a new address. Approval stays disabled until one is entered. Applications are never dropped because of a clash.
  • Early-Access Waitlist tab: signups from countries that have not launched yet. These record interest only — they cannot be approved, no store is created and nobody is charged.
  • Needs more information: instead of approving or rejecting, the admin can send the applicant a question (status: needs_info with reviewNotes). The application stays in review and can be approved later.
  • Country launch: when a new country is added to the website's LAUNCHED_COUNTRIES, POST /api/admin/waitlist/notify with { "country": "AE" } emails everyone on that country's list once, inviting them to sign up.

"Needs more information" and the country notification are available through the API; the portal does not have buttons for them yet.

Figure 4.8 — Platform security & audit logs

A forensic, platform-wide event stream (PlatformAuditLogs.tsx). Every sensitive action — sign-ins, provisioning, credential and password changes, database access, product and branding edits — is recorded with timestamp, actor, role, target store, IP and metadata.

5. Store Provisioning Workflow

Figure 5.1 — Provision New Store dialog

A store can be provisioned from an approved application or directly from Provision Store. The dialog (ProvisionStoreModal.tsx) collects:

  • Store / brand name and subdomain slug (<slug>.orvexacloud.in).
  • Owner full name, owner account email and WhatsApp / phone.
  • What will you sell? — a niche from the store-type picker (Section 8), which pre-fills suggested categories.
  • Store categories — editable chips; add or remove any category.
  • Subscription plan: Starter, Growth Pro or Enterprise Plus.

What happens on submit

  1. A tenant record is created in the master database with status, plan and subscription details. The subscription starts as a 30-day trial priced from the plan catalog.
  2. An isolated database name orvexa_tenant_<slug> is assigned (server/src/services/tenantProvisioner.ts).
  3. An initial merchant password is generated and stored as a bcrypt hash.
  4. When running locally, the store's frontend folder src/tenants/<slug>/ is created from the template (Section 7.2), together with a tenant.env that contains no passwords or secrets. In production (read-only filesystem, NODE_ENV=production, Vercel, or TENANT_SCAFFOLDING=off) this step is skipped: all configuration lives in MongoDB, and a developer creates the folder with npm run store:create before the next deploy.
  5. A secure password-reset link is sent to the owner email ("zero-knowledge handover"), so the admin never needs to know the owner's final password.
  6. The event is written to the audit trail as STORE_PROVISIONED.
New stores start blank: they use the shared storefront design but contain no products, photos or demo content — only the chosen categories and niche-appropriate default text, which the owner can then customize.

9. Backend API Reference

The Express app (server/src/app.ts) mounts four routers. Bodies are JSON (5 MB limit, enough for inline product images), except the signed website signup routes, which read the raw body. Rate limits: 300 requests per 15 minutes globally, 10 per 15 minutes on credential endpoints (login, forgot/reset/change password, bootstrap), 60 per minute on /api/public, plus a checkout limiter on orders and reviews. Errors never expose internal details; unknown /api paths return 404 and oversized bodies 413.

GET /api/health reports signupIntake and decisionEmail as on or off, so you can confirm the signing secret and Resend are configured.

Admin requires a super admin JWT (requireAdmin). Seller requires a seller JWT for the same store (requireSeller + requireTenantAccess).

9.4 Tokens

  • Access tokens: JWT (HS256) signed with JWT_SECRET, lifetime ACCESS_TOKEN_TTL (default 1 hour), carrying user ID, role and tenant. Tokens issued before an owner's last password change are rejected.
  • Refresh tokens: signed with JWT_REFRESH_SECRET, 30 days, single use, stored server-side only as a SHA-256 hash in the RefreshToken collection with a TTL index that auto-deletes expired tokens.
  • In production the server refuses to start unless both secrets are at least 32 characters and different from each other.
  • Passwords are hashed with bcrypt; failed logins take the same time whether or not the account exists, and return the same message.

9.5 Website signup intake — /api/public

The marketing website forwards each store signup to this backend (contract: SUPER_ADMIN_API.md in the developer handoff). These routes need no admin login; instead each request is signed with a shared secret. They are mounted before the JSON body parser so the signature is checked against the exact raw bytes, and are rate-limited to 60 requests per minute.

MethodPathDescription
POST/signupsReceive a signup. Stores the plan, launch country, migration request, consent evidence and attribution. Early-access signups become waitlist entries; live ones become pending applications.
GET/slug-available?slug=Optional live check used by the signup form. Returns {available}.

Request signing

  • Headers: X-Orvexa-Timestamp (Unix seconds), X-Orvexa-Signature: sha256=<hex> and Idempotency-Key.
  • The signature is HMAC-SHA256 over "<timestamp>.<raw body>" (an empty body for the GET). It is compared in constant time, and requests older than 5 minutes are rejected.
  • SIGNUP_SIGNING_SECRETS accepts a comma-separated list, so a new secret can be added before the old one is removed.

Responses

CodeMeaning
201Accepted: {applicationId, status} where status is pending_review or early_access.
409Same Idempotency-Key already received; returns the original applicationId. No duplicate row is created.
400 / 422Unreadable JSON or a missing required field. Final — the website does not retry.
401Bad or expired signature.
503Intake not configured or the database is unavailable. The website retries.

A requested address that is reserved (for example admin, shop, help) or already taken is kept and flagged for the admin, and the owner is emailed to pick another. Prices in the payload are informational only; the store is always billed from the server's plan catalog. The website sends the receipt email; this backend sends only the decision emails (approved, needs more information, rejected), the address-clash email and the early-access launch email, via Resend when RESEND_API_KEY and MAIL_FROM are set (otherwise they are logged). Each one-time email carries a Resend idempotency key, so a retry never sends a second copy.

If SIGNUP_NOTIFY_EMAIL is set, the team receives a short alert for each new signup (reference, plan, country, store address and any migration request). It deliberately contains no owner contact details; staff open the application in the portal.

13.4 Email with Resend

The platform sends decision, address-clash and early-access launch emails through Resend (free plan: 3,000 emails a month, 100 a day at the time of writing). Setup takes about 30 minutes, once:

  1. Create a Resend account with a company email address (no card needed).
  2. Add the sending domain mail.orvexacloud.in (a subdomain keeps email reputation away from the website's domain).
  3. Add the three DNS records Resend shows (MX and SPF TXT on send.mail, DKIM TXT on resend._domainkey.mail) in Cloudflare, with the proxy set to DNS only, or let Resend add them with "Sign in to Cloudflare". Then click Verify.
  4. Add a DMARC TXT record: name _dmarc, value v=DMARC1; p=none;.
  5. Create an API key with Sending access, limited to mail.orvexacloud.in. It is shown once; keep it in a secret manager.
  6. Set RESEND_API_KEY, MAIL_FROM="Orvexa Cloud <hello@mail.orvexacloud.in>" and MAIL_REPLY_TO as secret settings on the backend host, never in the repository.
  7. Check that GET /api/health shows "decisionEmail": "on", then approve a test application addressed to yourself.
The marketing website's connector uses its own Resend settings for the "we received your application" receipt. The same domain and a separate key can be used for both.

13.5 Connecting a store to its own database

To move a store onto a dedicated MongoDB Atlas cluster without putting the password in the repository:

cd server
$env:TENANT_MONGO_URI="mongodb+srv://<user>:<password>@<cluster>.mongodb.net/?appName=<name>"
npm run tenant:set-db -- lunar
Remove-Item Env:TENANT_MONGO_URI

The script connects to the cluster first and only then saves the URI on the store's record in the master database. If the URI names no database, orvexa_tenant_<slug> is used. The master database (MONGODB_MASTER_URI) must be reachable. A new database starts empty.

14. Security Notes & Production Checklist

14.1 Controls already in place

  • Admin-only sign-in gate at launch with a 5-attempt / 60-second lockout.
  • Short-lived access tokens (1 hour) and single-use refresh tokens stored hashed with automatic expiry; sessions end on password change, suspension or staff removal.
  • bcrypt password hashing, uniform login errors and timing.
  • Role guards (requireAdmin, requireSeller, requireStaff) and tenant isolation (requireTenantAccess); the store always comes from the URL and is checked against the token.
  • Checkout ignores client prices: totals, discounts and shipping are computed on the server and stock is reserved atomically.
  • Rate limiting on credential endpoints, the public signup API, checkout and globally.
  • Password-reset links are single use and time limited, are only ever emailed, and are built from PUBLIC_APP_URL, never from request headers.
  • Website signups are accepted only with a valid, recent HMAC signature, and repeats are de-duplicated by idempotency key.
  • Security headers on every response, exact-origin CORS, request size limits and generic error messages.
  • Credentials, password hashes and database URIs are never written to disk or returned by the API.
  • A complete audit trail of logins, provisioning, credential and content changes.
  • 46 automated integration tests, including the cross-tenant access tests.

14.2 Before going live

Not production-ready yet. Parts of the dashboard and storefront still read and write browser-side demo data, and Razorpay billing is not integrated. Keep VITE_DEMO_MODE unset in production builds so the demo fallbacks stay off.
  1. Leave VITE_DEMO_MODE unset (production builds then never use the browser-side credential fallback).
  2. Create the real super admin with /api/auth/admin/bootstrap and a strong, unique password; then remove ADMIN_BOOTSTRAP_KEY.
  3. Set two different random JWT_SECRET and JWT_REFRESH_SECRET values of 32+ characters (the server refuses to start in production otherwise).
  4. Keep SUPABASE_SERVICE_ROLE_KEY and MongoDB URIs server-side only.
  5. Enforce the admin lockout on the server as well (the current lockout is in the browser and can be reset by clearing session storage); consider adding two-factor authentication.
  6. Consider rate-limiting or signing POST /api/admin/audit-logs, which is open so storefronts can record events.
  7. Restrict CORS_ORIGIN to the real production domains.
  8. Change all demo store passwords or remove the demo stores.
  9. Generate the signup signing secret, store it in a secret manager and share it with the website's connector through that manager — never by chat or email.
  10. Verify a sending domain in Resend and set RESEND_API_KEY, MAIL_FROM and PUBLIC_APP_URL so owners receive working approval links.
  11. Confirm where customer data is actually hosted before stating any data-residency region in the legal pages.
  12. Build the remaining handoff promises: Razorpay subscriptions and webhooks, automatic trial / grace-period / read-only transitions, GST invoices, data export after cancellation, and the Growth Pro feature gating (custom domain, analytics and coupons, WhatsApp updates, Magic AI).
  13. Rotate any database password that has been shared in chat or email.
